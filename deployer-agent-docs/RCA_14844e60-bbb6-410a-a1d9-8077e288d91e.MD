# RCA — Cortexia Optical (eyecare-erp): Stripe "no configurado" 503 on /my-plan (PRODUCTION)

Deployment: `eyecare-erp` · active run `14844e60-bbb6-410a-a1d9-8077e288d91e` (redeploy, success) · template `fastapi_react_mongo_shadcn_base_image` · live at https://eyecare-erp.emergent.host

## Symptom (confirmed in prod)
Runtime logs on the active run show repeated `POST /api/billing/checkout HTTP/1.1 503 Service Unavailable` — the code path `_stripe_configured()==False` → `_not_configured_error()` (the "Stripe aun no esta configurado…" toast).

## How the key is resolved (backend/routes/billing.py)
```python
_ENV_PATH = Path(__file__).resolve().parent.parent / ".env"   # backend/.env (bundled in image)
def _resolve_stripe_key() -> str:
    env_key = (os.environ.get("STRIPE_API_KEY") or "").strip()
    if not env_key or env_key == "sk_test_emergent":
        file_key = (dotenv_values(_ENV_PATH).get("STRIPE_API_KEY") or "").strip()
        if file_key and file_key != "sk_test_emergent":
            return file_key
    return env_key
def _stripe_configured() -> bool:
    k = _resolve_stripe_key()
    return k.startswith("sk_") and k != "sk_test_emergent"
```
Verified in the eph sandbox against the REAL bundled `backend/.env`:
- Bundled `backend/.env` ⇒ `STRIPE_API_KEY=sk_test_emergent` (the platform placeholder). **The `.env` fallback is therefore DEAD in the deployed image — it can never supply a real key in prod.**
- `configured()` truth table (os.environ value → result): empty→False, `sk_test_emergent`→False, `sk_test_…`(real)→True, `sk_live_…`→True, `pk_…`→False, `rk_…`→False, quoted `"sk_live_…"`→False.

## Env precedence in prod — does Manage→Secrets win? (Q2)
YES. There is **no `load_dotenv(override=True)` anywhere.**
- `backend/db.py:9` → `load_dotenv(ROOT_DIR / '.env')` (default `override=False`) → does NOT overwrite an already-injected env var.
- `billing.py` uses `dotenv_values()` which only READS the file; it never mutates `os.environ`.
- Therefore `os.environ["STRIPE_API_KEY"]` == the value injected from the deployment secret store (the Manage→Secrets value). The bundled `.env` placeholder does **NOT** shadow os.environ.
- The docstring's premise ("la plataforma inyecta el placeholder `sk_test_emergent` en el entorno del proceso") is true **only in PREVIEW/agent-env**, NOT in production. This is the root of the developer's misconception.

## Secret store state (list_secrets, active run) (Q1)
- `STRIPE_API_KEY`: present, **not empty**, and **`matches_expected:false`** vs `sk_test_emergent` → the store value is NOT the placeholder.
- `WEBHOOK_CRON_SECRET`: present, not empty.

## Root cause (Q1/Q2/Q3)
Since os.environ == the injected store value (no override) and the store value is non-empty & non-placeholder, yet the live endpoint still reports "not configured", **the effective `STRIPE_API_KEY` the running backend sees does not start with `sk_`.** Two consistent explanations (cannot be fully separated without the raw value, which no tool exposes):

1. **Wrong / malformed stored value (most likely):** the value in Manage→Secrets is not a valid secret key — e.g. a **publishable** key `pk_live_…`, a **restricted** key `rk_…`, or a valid `sk_` key wrapped in quotes / with leading-trailing whitespace or a stray label. Any of these makes `startswith("sk_")` false → 503, even though it is "not the placeholder."
2. **Stale running pod:** the Secrets value was edited in the UI AFTER the current pod (run `14844e60`, created ~03:15) was started; the store now shows the new value but the live process still holds the value injected at pod-create time. Manage→Secrets edits require a redeploy to reach the running process.

Note: the dead `.env` fallback is NOT what causes this failure (os.environ is authoritative), but it is a latent bug and it hard-codes the developer's wrong mental model.

## Recommended fix (Q3 — correct BYOK for native `stripe` SDK)
- **Do NOT rename the secret.** `STRIPE_API_KEY` is already the correct name and already wins in `os.environ` in production.
- **Operational (user):** In Manage→Secrets set `STRIPE_API_KEY` to the real **SECRET** key `sk_live_…` (or `sk_test_…`) — never the publishable `pk_…` or restricted `rk_…` key — with no surrounding quotes or spaces. **Save, then redeploy** so the running pod picks it up.
- **Code (E1 to apply in source):** simplify resolution to trust `os.environ` as the single source of truth in prod and drop the dead `.env` fallback (or gate it to local preview only). Example:
```python
def _resolve_stripe_key() -> str:
    return (os.environ.get("STRIPE_API_KEY") or "").strip()
def _stripe_configured() -> bool:
    k = _resolve_stripe_key()
    return k.startswith("sk_") and k != "sk_test_emergent"
```
Optionally, to help users self-diagnose, log the detected prefix (never the full key), e.g. `key present, prefix=<first 3 chars>, len=<n>` when `_stripe_configured()` is False.
